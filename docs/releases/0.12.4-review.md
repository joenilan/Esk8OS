# Firmware 0.12.4 candidate review

This branch prepares firmware source for review and hardware validation. It does
not authorize stable publication. The public release stays on 0.12.1.

## Reviewed scope

- The six TFT/OLED/headless and no-BMS/Daly environments, pinned Linux build
  dependencies and the local PlatformIO wrapper.
- The BMS lifecycle/target interface and the existing Daly adapter. Characteristic
  0007 reports the driver and accepts a bounded address-only request; callbacks
  queue input and the main loop validates and persists only the BMS target key.
- Target mutation is dashboard/stationary-only and blocked while remote control
  owns the path. The poll task owns reconnection; revision checks invalidate
  snapshots from an earlier target, including an in-flight poll.
- Console selection/forget and the documented app/firmware contract. No additional
  BMS protocol is advertised. No motor or battery protection settings are written.
- Candidate packaging requires all six images and records a full source commit.
  Clean staging checks the tree before/after building and the embedded identity
  in every image. It refuses stale/dirty binaries, and never uploads or rebuilds
  a website. Candidate metadata explicitly records pending hardware validation.

The working checkout's line-ending-only changes, machine/agent settings, local
security-scan notes, historical handoff edits, retired website edits and proposed
licensing texts are outside this source commit. Existing third-party notices
remain; no first-party license is adopted here.

## Build and host validation

Run from a clean checkout of the reviewed commit:

```bash
~/.local/share/esk8os-platformio/bin/python -B -m unittest discover -s tests -v
CXX=clang++ EVEE_SANITIZERS=1 ~/.local/share/esk8os-platformio/bin/python -B -m unittest discover -s tests -p test_daly_target.py -v
~/.local/share/esk8os-platformio/bin/python scripts/publish_release.py --dry-run --require-clean --output-dir /path/to/new/candidate
```

Check SHA-256 sidecars and manifests, ESP32-S3 image checksums/digests, embedded
version/commit and both 4 MiB OTA slot bounds. Build success and host policy tests
do not establish hardware behavior. Local packages and build logs are not source
files to commit or publish to GitHub.

## Hardware gate — pending

These checks require the stopped vehicle and its real board/BMS. None is claimed
complete by this source branch or by the candidate metadata.

- **Upgrade data preservation:** before an authorized update, archive the device
  session logs and record the current firmware, settings, odometer, learned
  calibration and partition layout. Update the matching variant without erasing
  flash/NVS. Compare those values and the archived/existing log contents afterward;
  account for new session records rather than treating their creation as loss.
- **Target persistence:** with Demo off, select the actual BMS through the app or
  USB console and confirm characteristic 0007 readback. Restart/power-cycle the
  ESP32; verify the same selection is retained and reconnects without reselection.
- **Fresh real data:** verify Demo remains off and characteristic 0006 shows fresh
  live pack/cell readings from that BMS after reconnect. Check freshness/age and
  compare readings against the pack's own evidence; finding an advertisement or
  matching target readback alone is not a pass.

Record the hardware/environment, exact candidate commit and binary SHA-256,
baseline/after evidence, test date and outcome for each item. Preserve failures
and keep publication pending until all checks and maintainer review pass.
No erase, calibration reset, protection-limit change or substitute demo evidence
may be used to obtain a passing result.
